## 1. Единый вход по SMS-коду — сделано

Причина была в `check-code`: он искал только клиентов, поэтому служебный
номер получал `is_new_user: true`. `verify-code` ошибался так же и завёл бы
сотруднику клиентский дубль поверх служебного аккаунта.

Оба теперь ходят в один резолвер. Порядок разрешения номера:

1. **Служебный аккаунт этого карго.** Сотрудник живёт внутри карго.
2. **Супер-владелец** — по номеру, без привязки к карго.
3. **Клиент** — глобально по номеру.

Служебный аккаунт стоит впереди клиентского намеренно: иначе оператор,
который ещё и клиент другого карго, попадал бы на смене в клиентскую часть.

Анкета (`pickup_point_id`, `full_name`) к сотруднику **не применяется**: ПВЗ
у него — место работы, и данные с экрана регистрации молча перевели бы
оператора в другой пункт. Для клиентов поведение прежнее.

### Прогон на проде

```
1. send-code   → 200  {"detail":"SMS code sent","channel":""}
2. check-code  → 200  {"valid":true,"is_new_user":false}
3. verify-code → 200  is_new_user: false
   флаги: is_staff=true, is_cargo_admin=true, is_china_staff=false, is_superuser=false
   allowed_tabs: [scan, issue, warehouse, clients, delivery, staff, pickup,
                  tariff, delivery_tariff, analytics]
4. GET profile/ → те же четыре флага
```

`user` в `verify-code` сериализуется тем же сериализатором, что в
`auth/token/` и `GET profile/` — это один класс, разъехаться они не могут.

### Чеклист

- [x] `send-code` принимает номер сотрудника без клиентского профиля
- [x] `check-code` для сотрудника отдаёт `is_new_user: false`
- [x] `check-code` по-прежнему не гасит код
- [x] `verify-code` без анкеты отдаёт сессию сотрудника
- [x] в `verify-code.user` все четыре флага и `allowed_tabs`
- [x] `GET profile/` отдаёт те же флаги
- [x] `password` в `manage/staff/` стал необязательным
- [x] клиент-старожил входит как раньше
- [x] новый клиент регистрируется как раньше, с `client_code` и QR
- [x] тестовый номер для ревью магазинов работает
- [x] `auth/token/` не удалён

### `password` в `manage/staff/`

Необязателен. Без него сотруднику ставится **непригодный** пароль, а не
пустой: пустой прошёл бы проверку в `auth/token/`. Поле можно убрать из
формы создания.

## 2. Тестовый доступ

```
телефон: +996999000315
карго:   TST (id 5)
код:     0000 (фиксированный, SMS не приходит, не истекает)
```

Проходит `send-code` → `check-code` → `verify-code`. Аккаунт — админ карго,
видит все вкладки.

Отдельное тестовое карго, не боевое: сканы и смены статусов в нём никуда не
уходят. Карго **активно** (иначе `send-code` его не примет), но снято с
витрины — в `GET cargo-companies/` его нет, клиент при регистрации его не
увидит.

| что | сколько |
|---|---|
| ПВЗ | 2 (Бишкек, Ош — разные префиксы кодов) |
| клиенты | 2, коды `TSTB0001` и `TSTO0001` |
| посылки | 4: на складе в Китае, в пути, в ПВЗ, выдана |

Два ПВЗ специально: ошибки со скоупом видны только когда есть второй пункт,
в который оператор попадать не должен.

Запасной вход по паролю (на случай, если с OTP что-то пойдёт не так) —
отдельным сообщением.

## 3. Схемы и параметры

### `GET manage/dashboard/`

**Два ключа у вас не сходились** — `clients_count` и `by_status` бэк отдавал
как `users_count` и `parcels_by_status`, то есть две плитки были мертвы.
Добавлены синонимы: теперь работают оба имени, значения одинаковые (это
проверяется тестом). Переименовывать не стали — на старых именах живёт
веб-панель.

Весь ваш список подтверждён:

```
period_revenue_kgs    period_issued_count   period_received_count
period_avg_check_kgs  period_avg_weight_kg  period_weight_kg
issued_revenue_kgs    potential_revenue_kgs total_weight_kg
parcels_count         orders_count          clients_count
pickup_points_count   parcels_pending_count price_per_kg_kgs
by_status
```

Сверх него отдаются: `cargo{id,title,slug}`, `pickup{id,title}`,
`period{key,from,to}`, `timeseries[{date,count,revenue}]`,
`top_clients[{client_code,full_name,count,revenue}]`,
`by_pickup[{title,count,revenue}]`, `issued_count`, `issued_weight_kg`.

Смысл двух, который легко перепутать: `potential_revenue_kgs` — стоимость
доставки **всех** посылок, а не только выданных; `parcels_pending_count` —
сканы без клиента.

Query-параметры: `period` (`today|7d|30d|90d|365d|all`, по умолчанию `30d`),
`from`/`to` (`YYYY-MM-DD`, перекрывают `period`), `pickup_point`.

### Имя параметра поиска

Костыль с тремя именами можно убрать — но не срочно: **принимаются все три**,
`q`, `search` и `query`. Ваш текущий build работает как есть.

Канонично: `q` в `clients/search/`, `search` в `manage/clients/`.

### `GET manage/clients/`

Параметры: `search` (+синонимы), `pickup_point`, `limit`, `offset`.
Ответ — `ClientListSerializer`: `id`, `full_name`, `phone`, `client_code`,
`pickup_point`, `pickup_point_title`, `orders_count`, `parcels_count`,
`push_enabled`, `created_at`.

`pickup_point` — это переключатель ПВЗ в шапке. У привязанного к ПВЗ
оператора он игнорируется: его скоуп уже задан пунктом, и чужой id спрятал
бы от него его же клиентов.

### `GET manage/clients/{id}/history/`

`{client{...}, orders[...], parcels[...]}` — объявлено в схеме.

### `GET clients/search/`

До 10 записей: `id`, `full_name`, `phone`, `client_code`,
`pickup_point_title`. Пустой запрос отдаёт `[]`.

### `GET manage/city-delivery/`

`?status=`, `?limit`, `?offset` работают. Добавился `?pickup_point=` —
переключатель ПВЗ раньше на этот раздел не действовал вовсе.

## 4. Остальное из списка

### Фото в рассылке

```
POST /api/manage/notifications/   (multipart/form-data)
title, body, pickup_points[], send_push, image
```

JSON по-прежнему принимается — поле необязательное.

Картинка приходит в `GET manage/notifications/` и в `GET notifications/` у
клиента полем `image`. Файл сохраняется один раз на всю рассылку: рассылка —
это N одинаковых уведомлений, и файл в каждом дал бы N копий одной картинки.

### `push_enabled`

Есть в `GET manage/clients/`. Добавился `PATCH manage/clients/{id}/`:

```
PATCH /api/manage/clients/{id}/   {"push_enabled": false}
→ полная карточка клиента
```

У клиентов, которые настройки ни разу не трогали, приходит `true`. Чужой
клиент — `404`.

### Значения `allowed_tabs`

Полный набор (объявлен в схеме перечислением):

```
scan  issue  warehouse  china  clients  delivery  staff
pickup  tariff  delivery_tariff  analytics  overview  delivery_address
```

Оператору **выдаются** только эти:

```
scan  issue  warehouse  clients  delivery  staff
pickup  tariff  delivery_tariff  analytics
```

`china` — только у оператора склада в Китае, `overview` и
`delivery_address` — только у супер-владельца. Админ карго получает весь
выдаваемый набор независимо от того, что записано в поле.

`allowed_tabs` в `profile/` и `verify-code` — это **эффективный** список с
учётом роли, по нему можно резать меню напрямую. Незнакомые ключи при
записи через `manage/staff/` молча отбрасываются, ошибки не будет.

### Ответы массовых операций

```
POST manage/parcels/bulk-scan/
→ { "created": 1, "updated": 1,
    "errors": [ { "index": 2, "track_number": "", "error": "Пустой трек-номер" } ] }

POST manage/parcels/bulk-status/
→ { "updated": 2,
    "errors": [ { "index": 1, "id": 7, "error": "Посылка не найдена" } ] }
```

Обе схемы объявлены. Две тонкости: `index` — позиция строки в присланном
массиве (по ней подсвечивайте строку и давайте переотправить только её);
в `bulk-status` посылка, уже стоявшая в нужном статусе, не попадает ни в
`updated`, ни в `errors`.

## 5. Ответы на вопросы раздела 7

**7.1. Есть ли карго у супер-владельца?**

Может не быть. Раньше он из-за этого физически не мог запросить код —
`send-code` искал пользователя в пределах карго. Теперь, если номер
принадлежит супер-владельцу, `send-code` проходит **с любым** валидным
`cargo_id`. То есть экран входа можно не менять: пусть вводит код любого
карго, вход сработает.

Отдельно: в профиле у него `"cargo": null` — поправьте падение, оно реально
может прийти.

**7.2. Один номер — и сотрудник, и клиент?**

Один аккаунт с флагами, как вам и удобнее. Если по номеру в этом карго есть
служебный аккаунт, войдёт именно он, и клиентский дубль не создаётся.
Переключение между панелью и клиентской частью — на вашей стороне, сессия
одна.

**7.3. Один номер в двух разных карго?**

Да, это два разных аккаунта, путаницы не будет. Сотрудник ищется в пределах
`cargo_id`, а `login_key` у него — `<cargo>:<phone>`. Проверено тестом:
оператор карго A и клиент карго B с одним номером не пересекаются, и при
входе в карго A возвращается оператор.

Нюанс, который стоит знать: **клиентский** аккаунт на номер один на всю
платформу. Если номер уже клиент карго B и вы войдёте с `cargo_id` карго A,
не имея там служебного аккаунта, вернётся тот же клиент карго B — нового не
создастся.

**7.4. Куда уходит SMS сотруднику?**

Тем же каскадом WhatsApp → SMS, что и клиентам. Отдельного канала нет.

## 6. Что не менять без предупреждения

`GET /api/parcels/` **без** `?limit=` отдаёт голый массив — как до
пагинации. Страница включается только когда вы прислали `limit`, и тогда
приходит `{count, next, previous, results}`. Сделано так намеренно: старые
установленные приложения не разбирают объект вместо массива.

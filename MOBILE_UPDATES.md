Изменения бэкенда, которые касаются **клиентского** Flutter-приложения. Web-панель
(сотрудники/владельцы) сюда не входит.

Кратко:

## Push-токен — отправлять при каждом запуске, а не только при входе

### Что видно на сервере (07.10)

```
новых токенов за 14 дней            Android 162   iOS 222
  из них сразу после входа по SMS            159       207
повторных отправок уже известного токена       0         0
```

Приложение присылает токен **только при входе**. Повторных отправок нет вообще —
иначе у существующих токенов обновлялась бы дата.

Токен FCM меняется при обновлении приложения, переустановке, переносе на новый
телефон, а также по решению самого FCM. Сессия при этом сохраняется — на iOS
она лежит в Keychain и переживает даже удаление приложения. Клиент заново не
входит, новый токен на сервер не приходит, у сервера остаётся мёртвый — и push
перестаёт доходить молча.

Прогнали все токены, которые в базе числятся живыми, через FCM:

```
iOS       рабочих 667, мёртвых  37
Android   рабочих 308, мёртвых  92
клиентов без единого рабочего токена: 97 (из них 22 на iPhone)
```

Этим 97 клиентам уведомления не приходят вообще, и сами они это не исправят,
пока не выйдут и не войдут заново.

### Что поменять

Отправлять токен **при каждом запуске, если пользователь залогинен**, и **при
каждом обновлении токена**. Регистрация на сервере идемпотентна: повторный
`POST /api/device-tokens/` с тем же токеном просто обновит запись, с чужим —
перепривяжет к текущему пользователю. Слать часто безопасно.

> **Исправлено на сервере 07.10.** До этого повторная регистрация уже известного
> токена отдавала `400` («device token with this token already exists»):
> автоматический валидатор уникальности срабатывал раньше логики обновления.
> Если вы видели такую ошибку — это была наша сторона, теперь повтор проходит.
>
> Заодно закрылась дыра со сменой аккаунта на одном телефоне: если при выходе
> `DELETE` не дошёл (нет сети), токен оставался у прежнего аккаунта, и его
> уведомления приходили на чужой телефон. Теперь вход нового пользователя
> перепривязывает токен к нему.

```dart
Future<void> syncPushToken() async {
  final messaging = FirebaseMessaging.instance;

  // На iOS getToken() вернёт null, пока не пришёл APNs-токен — ждём его.
  if (Platform.isIOS) {
    for (var i = 0; i < 10; i++) {
      if (await messaging.getAPNSToken() != null) break;
      await Future.delayed(const Duration(milliseconds: 500));
    }
  }

  final token = await messaging.getToken();
  if (token == null) return;
  await api.post('/api/device-tokens/', {
    'token': token,
    'platform': Platform.isIOS ? 'ios' : 'android',
  });
}

// 1. При старте приложения, если сессия есть (не только после входа):
if (auth.isLoggedIn) await syncPushToken();

// 2. Один раз подписаться на смену токена:
FirebaseMessaging.instance.onTokenRefresh.listen((token) {
  if (!auth.isLoggedIn) return;
  api.post('/api/device-tokens/', {
    'token': token,
    'platform': Platform.isIOS ? 'ios' : 'android',
  });
});

// 3. После входа — как сейчас: syncPushToken().
// 4. При выходе — как сейчас: DELETE /api/device-tokens/ {token}.
```

Ошибку отправки токена показывать пользователю не нужно, но и глушить молча не
стоит — залогируйте: без токена уведомления не придут, а узнать об этом иначе
будет нельзя.

### Как проверить

Залогиниться, обновить сборку поверх (без выхода), открыть приложение. На
сервере у этого пользователя должна обновиться дата токена. Сообщите номер — мы
посмотрим по базе и отправим тестовое уведомление.

После выпуска версии у каждого из 97 клиентов токен восстановится сам при
первом открытии приложения.
2. **Статусы посылок:** добавлены 3 новых статуса + авто-цепочка теперь реально идёт.
3. Поле `pickup_point` у посылки.

| Метод | URL | Auth | Описание |
|---|---|---|---|
| GET | `/api/delivery-address/` | да (любой залогиненный клиент) | Адрес склада с кодом этого клиента |

### Ответ (200)

```json
{
  "recipient_name": "张伟",
  "phone": "+8613800138000",
  "province": "广东省",
  "city": "广州市",
  "district": "白云区",
  "detail_address": "XX路 100号 315CARGO仓库",
  "instructions": "Обязательно оставьте свой код в адресе, иначе посылку не опознают.",
  "is_active": true,
  "region": "广东省广州市白云区",
  "recipient": "张伟",
  "one_line": "程先生 13250150777 广东佛山南海 里水镇和顺鹤峰1号仓315库东 x69610 ISI-0002",
  "detail_address_full": "里水镇和顺鹤峰1号仓315库东",
  "cargo_code": "x69610",
  "client_code": "C1234567",
  "updated_at": "2026-08-01T02:15:00Z"  
}
```

Поля:
- `recipient` — **收货人 = ФИО получателя** на складе. Именно это идёт в имя получателя в PDD. Берётся из карго клиента (у каждого карго свой человек на приёмке), фолбэк — общее ФИО, затем код клиента.
- `one_line` — **готовая строка для вставки** в PDD (умное распознавание / 智能填写): `收货人 телефон 省市区 детальный_адрес+приписка КОД_КАРГО КОД_КЛИЕНТА`. Оба кода уже внутри, индекса нет.
- `cargo_code` — **код карго клиента** (напр. `x69610`), новое поле. Пустая строка, если супер-владелец его ещё не задал — тогда его нет и в `one_line`.
- `region` — `省市区` одной строкой (провинция+город+район слитно).
- `phone`, `province`, `city`, `district`, `detail_address_full` — по отдельности (для ручного заполнения полей PDD). Индекс не нужен.
- `instructions` — памятка клиенту (показать рядом).
- `is_active` — если `false`, адрес не готов: экран лучше скрыть/задизейблить.
- `recipient_name` — сырое ФИО из панели; для показа клиенту используйте `recipient` (он с фолбэком).
- `client_code` — код текущего клиента отдельным полем (для ручного заполнения полей PDD: вместе с `cargo_code` дописывается в конец детального адреса).

### Что сделать в приложении

1. Экран/блок «Адрес для заказов в PDD» (в разделе PDD или профиле).
2. Дёрнуть `GET /api/delivery-address/` (JWT клиента).
3. Если `is_active == false` → показать «адрес ещё не настроен».
4. Показать поля + `instructions`. Дать кнопку **«Скопировать»**:
   - основная — копирует `one_line` (клиент вставляет одной строкой в 收货地址 → PDD сам разложит по полям);
   - опционально — копировать поля по отдельности (收货人=`recipient`, телефон, регион, адрес + `cargo_code` и `client_code` в конце адреса).
5. Подсветить, что **коды в конце адреса** убирать нельзя — без них коробку не опознают.

## 2. Статусы посылок — добавлены новые + авто-цепочка

### Новые статусы (backend snake_case)

В `ParcelStatus` добавьте **3 статуса** (сейчас в мобильной enum их нет — при их
получении текущий парсер кинет `ArgumentError`):

| Backend | Dart enum | Отображение (RU) |
|---|---|---|
| `in_storage` | `inStorage` | Отправлен на хранение |
| `in_transit` | `inTransit` | В пути |
| `processing` | `processing` | Классификация и обработка |

Полный список статусов сейчас:
`created`, `purchased`, `waiting_china_warehouse`, `arrived_china_warehouse`,
**`in_storage`**, `sent_to_kyrgyzstan`, **`in_transit`**, `arrived_kyrgyzstan`,
**`processing`**, `at_pickup_point`, `city_delivery`, `delivered`, `issued`, `cancelled`.

```dart
enum ParcelStatus {
  created,
  purchased,
  waitingChinaWarehouse,
  arrivedChinaWarehouse,
  inStorage,          // НОВОЕ
  sentToKyrgyzstan,
  inTransit,          // НОВОЕ
  arrivedKyrgyzstan,
  processing,         // НОВОЕ
  atPickupPoint,
  cityDelivery,
  delivered,
  issued,
  cancelled,
}

ParcelStatus parseParcelStatus(String value) => switch (value) {
      'created' => ParcelStatus.created,
      'purchased' => ParcelStatus.purchased,
      'waiting_china_warehouse' => ParcelStatus.waitingChinaWarehouse,
      'arrived_china_warehouse' => ParcelStatus.arrivedChinaWarehouse,
      'in_storage' => ParcelStatus.inStorage,
      'sent_to_kyrgyzstan' => ParcelStatus.sentToKyrgyzstan,
      'in_transit' => ParcelStatus.inTransit,
      'arrived_kyrgyzstan' => ParcelStatus.arrivedKyrgyzstan,
      'processing' => ParcelStatus.processing,
      'at_pickup_point' => ParcelStatus.atPickupPoint,
      'city_delivery' => ParcelStatus.cityDelivery,
      'delivered' => ParcelStatus.delivered,
      'issued' => ParcelStatus.issued,
      'cancelled' => ParcelStatus.cancelled,
      // на будущее лучше не кидать исключение, а вернуть fallback:
      _ => ParcelStatus.created,
    };
```

> **Важно:** сервер может добавлять статусы и дальше — в `parseParcelStatus`
> сделайте безопасный `_ => <fallback>` вместо `throw`, иначе новые статусы будут
> ронять экран трекинга.

### Порядок для таймлайна трекинга

`arrived_china_warehouse → in_storage → sent_to_kyrgyzstan → in_transit →
arrived_kyrgyzstan → processing → at_pickup_point → issued`.
(`city_delivery`/`delivered` — ветка доставки по городу.)

### Поведение

Промежуточные статусы (`in_storage`, `in_transit`, `processing` и т.д.) теперь
проставляются **автоматически по времени** после приёма на складе в Китае. Клиент
будет получать `parcelStatusChanged`-уведомления и видеть смену статуса в трекинге
без действий оператора. Отдельных экранов не требуется — просто корректно
показывать все статусы в истории/таймлайне.

### Обновление маршрута (сентябрь 2026) — нужен ещё один статус

Добавлен статус **`customs` — «На таможне»**. Внесите его в `ParcelStatus` и в
`parseParcelStatus` (`'customs' => ParcelStatus.customs`), в таймлайне ставьте
между `in_transit` и `at_pickup_point`. Если fallback `_ => …` у вас уже есть,
экран не упадёт, но статус будет отображаться неверно.

Сама цепочка сокращена и теперь выглядит так:

```
Прибыл на склад в Китае
   +1 день  → В пути        (in_transit)
   +7 дней  → На таможне    (customs)
   дальше — только реальный скан оператора
```

Что изменилось по существу: **таймер больше не объявляет прибытие**. Раньше
`arrived_kyrgyzstan` проставлялся автоматически на 9-й день, и пуш «Посылка
прибыла в Кыргызстан» уходил клиенту независимо от того, где посылка на самом
деле. По данным прода реальное время в пути — от 0.3 до 16 дней, поэтому
уведомление было ложным у большинства. Теперь `arrived_kyrgyzstan`,
`at_pickup_point` и всё, что дальше, приходят только от скана.

`processing` из авто-цепочки убран. Статус остаётся в списке (старые посылки в
нём есть), но новые в него больше не попадают.

## 3. Поле `pickup_point_title` у посылки

У посылки на бэкенде появился **физический ПВЗ приёмки** — куда её реально приняли.
Клиенту (в `/api/parcels/`) отдаётся **только название** этого ПВЗ; числовой id
клиентам не выдаётся.

- `pickup_point_title` — `String?` — название ПВЗ, где посылка (физический ПВЗ
  приёмки; если ещё не принята — ПВЗ из профиля клиента; иначе `null`).

Мобилке достаточно, при желании, показать `pickup_point_title` на статусе «В ПВЗ»
(«Заберите в: …»). Обязательных изменений нет — поле опциональное.

Добавьте в модель `Parcel`:
```dart
final String? pickupPointTitle; // название ПВЗ (для отображения)
```

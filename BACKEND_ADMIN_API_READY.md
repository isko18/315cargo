# Бэкенд для мобильной панели — что готово

Ответ на `BACKEND_ADMIN_API.md`. Всё перечисленное развёрнуто на
`https://315cargo.com` и работает.

Базовый URL: `https://315cargo.com/api/`
Авторизация: `Authorization: Bearer <access>` во всех запросах ниже.

---

## 1. Тестовый доступ

Отдельное **тестовое карго** — песочница, не боевые данные. Сканы и смены
статусов в ней никуда не уходят: живых клиентов у неё нет, а в списке карго
в клиентском приложении она не показывается.

```
POST /api/auth/token/
{ "login": "+996999000315", "password": "<пароль отдельным сообщением>" }
→ { "access": "...", "refresh": "..." }
```

Аккаунт — админ карго, видит все вкладки. В песочнице уже есть:

| что | сколько |
|---|---|
| ПВЗ | 2 (Бишкек, Ош — разные префиксы кодов) |
| клиенты | 2, коды `TSTB0001` и `TSTO0001` |
| посылки | 4: на складе в Китае, в пути, в ПВЗ, выдана |

Два ПВЗ — специально: ошибки со скоупом видны только когда есть второй
пункт, в который оператор попадать не должен.

Сбросить пароль или перезалить демо-данные: `manage.py create_test_cargo`
(идемпотентно, `--password` задаёт свой).

## 2. Правка посылки

Раньше карточка собиралась из трёх вызовов (`assign` + `weight` + `scan`), и
смена статуса через `scan/` писала в историю лишнюю строку приёмки — коробка
выглядела так, будто её снова сканировали. Теперь один запрос:

```
PATCH /api/manage/parcels/<id>/
```

Все поля необязательные, шлите только изменённые.

| поле | тип | примечание |
|---|---|---|
| `status` | строка | из списка статусов |
| `weight` | число | `delivery_price` пересчитается по тарифу карго |
| `client_code` | строка | привязка к клиенту; неизвестный код → 400 |
| `pickup_point` | id | ПВЗ чужого карго → 400 |
| `location` | строка | стеллаж/полка |
| `length_cm`, `width_cm`, `height_cm` | числа | `volume` считается сам, когда заданы все три |
| `payment_status` | `unpaid` / `partial` / `paid` | |
| `receipt_method` | `pickup` / `city_delivery` | |
| `delivery_address` | строка | при доставке по городу |
| `usd_rate` | число | курс на момент расчёта |
| `client_price` | число | итог к оплате, если он не равен расчёту по тарифу |
| `crating`, `packaging` | bool | обрешётка, упаковка |

Ответ — полная карточка посылки (тот же формат, что в `GET /api/parcels/`).

**`notified_at`** — только на чтение: ставится в момент, когда уведомление
реально ушло клиенту. Это факт отправки, а не поле ввода; в `PATCH` его
игнорируем.

Коды ответов: `404` — чужая посылка (существование не раскрываем),
`403` с `"code": "forbidden_status"` — оператору склада в Китае доступны
только китайские статусы.

### Объём

Считаем на бэкенде из габаритов. Вводить и размеры, и м³ — гарантированное
расхождение цифр, поэтому `volume` в `PATCH` не принимается.

## 3. Пачки

### Приём накладной

```
POST /api/manage/parcels/bulk-scan/
{
  "status": "at_pickup_point",
  "pickup_point": 9,
  "items": [
    { "track_number": "ABC1", "weight": "0.5" },
    { "track_number": "ABC2", "client_code": "TSTB0001" }
  ]
}
→ { "created": 1, "updated": 1, "errors": [ { "index": 2, "track_number": "", "error": "Пустой трек-номер" } ] }
```

Семантика строки — как у `scan/` (upsert по треку). **Каждая строка в своей
транзакции**: одна плохая не отменяет остальные, поэтому `errors` приходит
с `index` — покажите оператору, какие строки не прошли, и дайте
переотправить только их.

### Смена статуса выделенным

```
POST /api/manage/parcels/bulk-status/
{ "ids": [1, 2, 3], "status": "issued" }
→ { "updated": 2, "errors": [ { "index": 1, "id": 2, "error": "Посылка не найдена" } ] }
```

Чужая посылка попадает в `errors`, а не меняется молча.

## 4. Рассылки

```
GET    /api/manage/notifications/          список того, что уже разослано
POST   /api/manage/notifications/          разослать
DELETE /api/manage/notifications/<id>/     снять рассылку
```

```
POST { "title": "Поступление", "body": "Заказы до 23 августа",
       "pickup_points": [9], "send_push": true }
→ { "id": 403, "recipients_count": 19 }
```

`pickup_points` пустой — всем клиентам карго. ПВЗ чужого карго → 400.

Рассылка физически — это N уведомлений, по одному на клиента. В списке они
схлопнуты в одну строку (`recipients_count` — сколько получили), а `DELETE`
снимает её целиком: удаление одной копии оставило бы остальных с тем же
текстом.

`send_push: true` не значит, что push дойдёт до всех — клиент мог отключить
уведомления. Запись в списке он получит в любом случае.

## 5. Списки

`GET /api/parcels/` и `GET /api/parcels/history/` теперь **постраничные**
(`LimitOffsetPagination`):

```
{ "count": 1893, "next": "...?limit=50&offset=50", "previous": null, "results": [...] }
```

По умолчанию `limit=50`, максимум `500`. Читайте `results`, а не сам ответ.

Поиск в `GET /api/parcels/?search=` ищет по трек-номеру, коду клиента,
**имени и телефону клиента**.

`GET /api/manage/clients/` отдаёт `push_enabled` — у клиентов, которые ни
разу не трогали настройки, приходит `true`.

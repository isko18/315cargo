# OTP через WhatsApp — задача приложению

Коды подтверждения уходят в **WhatsApp** через официальный Cloud API от Meta.
Работает на проде.

| | |
|---|---|
| Отправитель | **+996 779 066 870**, имя профиля **Cargo OTP** |
| Канал в API | `whatsapp` |
| Запасной канал | SMS — **сейчас не работает**, см. §6 |

> **Контракт API не менялся. Ломающих изменений нет.**
> Уже выпущенные сборки продолжают работать. Правки нужны, чтобы экран не врал
> пользователю про SMS и чтобы работала кнопка автозаполнения.

---

## 1. Что изменилось для пользователя

Раньше код приходил обычным сообщением от неизвестного номера. Теперь — от
**верифицированного бизнес-аккаунта «Cargo OTP»** с зелёной галочкой, и текст
формирует сам WhatsApp.

**Текст сообщения мы больше не контролируем.** У шаблонов категории
authentication он фиксирован Meta и переведён ей же — что-то вроде
«*1234* — ваш код подтверждения» плюс приписка о безопасности и строка про
срок действия. Задать своё оформление нельзя.

Практический вывод: **не цитируйте текст сообщения в интерфейсе.** Формулировки
вида «пришлём сообщение “CARGO: ваш код…”» устарели — такого текста больше нет.
Ссылайтесь на отправителя: «код придёт в WhatsApp от Cargo OTP».

---

## 2. Что читать из ответа

`POST /api/auth/send-code/` отвечает:

```json
{ "detail": "SMS code sent", "channel": "whatsapp" }
```

| `channel` | Что показать |
|---|---|
| `"whatsapp"` | «Код отправлен в WhatsApp» |
| `"sms"` | «Код отправлен по SMS» |
| `""` | «Код отправлен» — нейтрально, без указания канала |

Поле есть всегда. `detail` оставлен прежним ради совместимости со старыми
сборками — **на него не завязывайтесь**.

Значение `"whatsapp"` не изменится при смене провайдера на стороне бэкенда:
это имя канала, а не название сервиса.

## 2.1 Проверка кода отдельным запросом

При регистрации экран кода и экран анкеты разделены, поэтому появился
**`POST /api/auth/check-code/`**:

```http
POST /api/auth/check-code/
{ "phone": "+996700000000", "code": "1234", "cargo_id": 4 }
```

```json
{ "valid": true, "is_new_user": true }
```

Он проверяет код и **не гасит его** — потом тот же код уходит в `verify-code`.
Неверный код даёт `400` и **тратит попытку** (их 5 на код).

**Почему так.** Раньше на экране кода приходилось звать `verify-code`, а он у
нового клиента требует ещё ФИО и ПВЗ. Их на этом шаге нет, и запрос падал —
но код при этом уже был потрачен. Клиент видел ошибку и ждал минуту нового
кода, хотя ввёл всё правильно.

**Как использовать:**

1. экран кода → `check-code`. `400` — показать «неверный код» прямо здесь;
2. `is_new_user: true` → показать анкету (ФИО, ПВЗ); `false` → анкету
   пропустить;
3. завершение → `verify-code` с тем же кодом, получить токены.

Для существующего клиента шаг 2 пропускается, и `check-code` можно не звать
вовсе — `verify-code` сразу отработает. Но проще звать всегда: один путь на
оба случая, и ошибка ввода показывается там, где человек её сделал.

## 3. Тексты на экране

Главная часть работы. Сейчас в приложении зашито «SMS», а код приходит в
WhatsApp: человек уходит проверять сообщения, не находит код, жмёт «отправить
ещё раз», упирается в троттлинг и идёт в поддержку.

Что заменить:

- заголовок и подсказку под полем ввода — по таблице выше;
- «Отправить SMS повторно» → «Отправить код повторно»;
- упоминания SMS в ошибках этого экрана;
- **экран «не приходит код»** — там должно быть про WhatsApp: проверить, что
  он установлен, и посмотреть чат от **Cargo OTP**.

Иконку тоже стоит менять по каналу — зелёный WhatsApp узнаётся быстрее текста.

## 4. Кнопка автозаполнения (опционально)

Шаблон одобрен с кнопкой типа **one-tap**: пользователь жмёт её прямо в
WhatsApp, система открывает приложение и передаёт код — вводить руками не надо.

Чтобы это заработало, в определении шаблона на стороне Meta должны быть
прописаны **`package_name`** и **`signature_hash`** вашей Android-сборки
(параметр `supported_apps`). Я проверить их не могу — нужен доступ к WhatsApp
Manager. **Посмотрите в шаблоне `cargo_otp`**, заданы ли они, и совпадает ли
хеш с тем, чем реально подписан релиз.

Важно, чего бояться не нужно: **если они не заданы или заданы неверно,
сообщение всё равно доставляется**, код виден текстом, вход работает. Ломается
только автоподстановка — кнопка не сделает ничего полезного.

Поэтому:

- поле ввода кода обязано нормально принимать **вставку из буфера** и ручной
  ввод — это основной путь, пока автозаполнение не настроено;
- не показывайте состояние «ждём код автоматически» при `channel: "whatsapp"`,
  пока не убедились, что one-tap реально работает на релизной сборке;
- проверять one-tap нужно **на релизной подписи**, а не на debug — у них разные
  signature hash.

Если автозаполнение не нужно, можно ничего не делать: копирование кода руками
работает всегда.

### Про SMS-автозаполнение

SMS Retriever / SMS User Consent на Android читают **только SMS**. Из WhatsApp
код не подставится. Не выпиливайте их — при `channel: "sms"` они сработают.

## 5. Троттлинг и повторная отправка

Ограничение прежнее: **один код в 60 секунд** на пару номер + карго, иначе
`429`.

Кнопку «Отправить повторно» держите заблокированной с обратным отсчётом.
Отсчёт должен переживать сворачивание приложения — иначе человек вернётся,
нажмёт и получит 429 без объяснения.

Канал при повторной отправке **может смениться**, поэтому `channel` надо
перечитывать при каждом ответе, а не запоминать один раз.

---

## 6. Про SMS: сейчас не работает

Аккаунт у SMS-провайдера тестовый — сообщения физически уходят только на один
номер из профиля. Для клиентов SMS не доставляется.

Что это значит на практике:

- на проде `channel: "sms"` **не появится**, пока аккаунт не оплатят;
- **клиент без WhatsApp сейчас войти не может**;
- ветку `"sms"` в приложении всё равно делайте — она понадобится сразу после
  оплаты, без выката новой сборки.

## 7. Контракт эндпоинтов (не изменился)

### Запрос кода

```http
POST /api/auth/send-code/
{ "phone": "+996700000000", "cargo_id": 4, "purpose": "login" }
```

`purpose`: `login` — существующий клиент, `register` — новый. При `login`
бэкенд проверяет, что клиент с таким номером есть в этом карго, иначе `400`.

### Подтверждение (гасит код, выдаёт токены)

```http
POST /api/auth/verify-code/
{ "phone": "+996700000000", "code": "1234", "cargo_id": 4,
  "pickup_point_id": 2, "full_name": "Иван Иванов" }
```

`pickup_point_id` и `full_name` обязательны только при регистрации. Ответ —
`access`, `refresh`, `user`, `is_new_user`.

Код — 4 цифры, живёт 5 минут, 5 неверных попыток сжигают его.

---

## 8. Пустой `channel`

Приходит в двух случаях: **тестовый номер** (код фиксированный, доставки нет —
нужен для ревью в сторах) и **отказ всех каналов** при включённом мастер-коде.
В обоих API отвечает `200`, потому что поток не прерывается. Показывайте
нейтральное «Код отправлен».

---

## 9. Как проверить

- **`channel: "whatsapp"`** — запросить код на номер с WhatsApp. Сообщение
  должно прийти от **Cargo OTP**, а не от неизвестного номера.
- **`channel: "sms"`** — на проде **не воспроизводится** (§6). Проверяйте на
  стенде или подменой ответа.
- **one-tap** — только на релизной сборке, после проверки `supported_apps`.

## 10. Приёмка

- [ ] `channel: "whatsapp"` → экран говорит про WhatsApp и про отправителя Cargo OTP
- [ ] `channel: "sms"` → экран говорит про SMS, SMS-автозаполнение работает (стенд)
- [ ] `channel: ""` → нейтральный текст
- [ ] Экран «не приходит код» говорит про WhatsApp, а не про SMS
- [ ] Нигде не цитируется старый текст сообщения с «CARGO:»
- [ ] Код вставляется из буфера и вводится руками
- [ ] Неверный код показывается ошибкой на экране кода, а не после анкеты
- [ ] После check-code тот же код проходит verify-code (не «сгорел»)
- [ ] `is_new_user: false` → анкета не показывается
- [ ] Повторная отправка со сменой канала — текст обновился
- [ ] Кнопка «повторно» заблокирована 60 с, отсчёт переживает сворачивание
- [ ] (если нужен one-tap) проверен на релизной подписи

# OTP через WhatsApp — задача приложению

Коды подтверждения уходят **в WhatsApp**. Переключение сделано на бэкенде и
уже работает на проде.

> ### ⚠️ SMS сейчас не работает — WhatsApp единственный канал
>
> Аккаунт у SMS-провайдера тестовый: он физически отправляет сообщения только
> на один номер, зашитый в профиле. Для клиентов SMS не доставляется вообще.
>
> Формально SMS остаётся в каскаде запасным каналом, и когда аккаунт оплатят,
> он заработает **без изменений в приложении**. Но проектировать экран нужно
> из того, что сейчас `channel` приходит либо `"whatsapp"`, либо пустой —
> `"sms"` в проде не появится, пока аккаунт тестовый.
>
> Практический вывод: **клиент без WhatsApp сейчас войти не может.** Если у
> вас есть экран «не приходит код» — там должно быть написано, что код
> приходит в WhatsApp, а не «проверьте SMS».

> **Контракт API не менялся. Ломающих изменений нет.**
> Старые версии приложения продолжают работать без обновления — они просто не
> знают, каким каналом пришёл код, и говорят про SMS. Ради этого и нужна
> правка: одно новое поле в ответе и тексты на экране.

---

## 1. Что изменилось на самом деле

Раньше был один канал. Теперь каскад:

```
POST /api/auth/send-code/
  └─ пробуем WhatsApp
       ├─ доставлено → channel: "whatsapp"      ← дёшево, приходит мгновенно
       └─ ошибка (нет WhatsApp у номера, шлюз лёг, сессия отвалилась)
            └─ пробуем SMS
                 ├─ доставлено → channel: "sms"
                 └─ ошибка → channel: "" (см. §5)
```

Откат на SMS заложен как штатный путь: у части клиентов WhatsApp не
установлен. **Но пока аккаунт SMS-провайдера тестовый, этот откат не
срабатывает** — такие клиенты код не получат. Ветку `"sms"` в приложении всё
равно делайте: она понадобится сразу, как аккаунт оплатят, и без неё придётся
выкатывать новую сборку.

Сам код, его длина (4 цифры), срок жизни (5 минут) и проверка через
`verify-code` — без изменений.

---

## 2. Что нужно сделать в приложении

### 2.1 Прочитать новое поле `channel`

`POST /api/auth/send-code/` теперь отвечает так:

```json
{ "detail": "SMS code sent", "channel": "whatsapp" }
```

| `channel` | Что показать пользователю |
|---|---|
| `"whatsapp"` | «Код отправлен в WhatsApp» |
| `"sms"` | «Код отправлен по SMS» |
| `""` | «Код отправлен» — без указания канала (см. §5) |

Поле есть всегда. `detail` оставлен прежним ради совместимости со старыми
сборками — **на него не завязывайтесь**, ориентир — `channel`.

### 2.2 Поправить тексты на экране ввода кода

Это главная часть работы. Сейчас на экране зашито «SMS», и при доставке в
WhatsApp человек уходит проверять сообщения, кода там не находит и жмёт
«отправить ещё раз» — то есть жжёт троттлинг и создаёт обращения в поддержку.

Что заменить:

- заголовок и подсказку под полем ввода — по таблице выше;
- кнопку «Отправить SMS повторно» → «Отправить код повторно»;
- любые упоминания SMS в текстах ошибок этого экрана.

Иконку тоже имеет смысл менять по каналу — зелёный WhatsApp узнаётся быстрее
любого текста.

### 2.3 Учесть, что автозаполнение из WhatsApp не работает

Если на Android используется SMS Retriever / SMS User Consent — он читает
**только SMS**. Из WhatsApp код автоматически не подставится.

Что с этим делать:

- **не убирать** SMS-автозаполнение: при `channel: "sms"` оно по-прежнему
  работает и экономит людям время;
- при `channel: "whatsapp"` не показывать состояние «ждём код автоматически»,
  иначе человек будет сидеть и ждать того, чего не произойдёт;
- поле ввода кода должно нормально принимать вставку из буфера — из WhatsApp
  код копируют вручную.

На iOS автозаполнение из SMS системное и на WhatsApp тоже не распространяется.

## 3. Контракт эндпоинтов (для справки, не изменился)

### Запрос кода

```http
POST /api/auth/send-code/
Content-Type: application/json

{ "phone": "+996700000000", "cargo_id": 4, "purpose": "login" }
```

`purpose`: `login` — для существующего клиента, `register` — для нового.
При `login` бэкенд проверяет, что клиент с таким номером есть в этом карго,
и иначе отвечает 400 с текстом «Пользователь не найден в этом карго-центре».

Ответ `200`:

```json
{ "detail": "SMS code sent", "channel": "whatsapp" }
```

### Подтверждение кода

```http
POST /api/auth/verify-code/
Content-Type: application/json

{ "phone": "+996700000000", "code": "1234", "cargo_id": 4,
  "pickup_point_id": 2, "full_name": "Иван Иванов" }
```

`pickup_point_id` и `full_name` обязательны **только при регистрации** нового
клиента. Ответ — `access`, `refresh`, `user`, `is_new_user`.

## 4. Троттлинг и повторная отправка

Ограничение осталось прежним: **один код в 60 секунд** на пару
номер + карго. Повторный запрос раньше — `429`.

Кнопку «Отправить повторно» держите заблокированной с обратным отсчётом на 60
секунд. Отсчёт должен переживать сворачивание приложения — иначе человек
вернётся, нажмёт и получит 429 без объяснения.

Важно: канал при повторной отправке **может смениться**. Первый код ушёл в
WhatsApp, второй — по SMS, если WhatsApp за эту минуту отвалился. Поэтому
`channel` надо перечитывать при каждом ответе, а не запоминать один раз.

---

## 5. Пустой `channel` — что это значит

`channel: ""` приходит в двух случаях:

1. **Тестовый номер** (`OTP_TEST_NUMBERS`) — код фиксированный, доставки нет.
   Нужен для ревью в сторах: он проходит `verify-code`, но никуда не шлётся.
2. **Все каналы отказали**, но включён мастер-код — вход не блокируется, хотя
   код клиенту не доставлен.

В обоих случаях API отвечает `200`, потому что поток не прерывается. На экране
показывайте нейтральное «Код отправлен», без обещания SMS или WhatsApp.

---

## 6. Как проверить

На тестовом номере (`+996700000000`, код `0000`) канал всегда пустой — он
проверяет только сам поток, но не доставку.

Чтобы увидеть реальные каналы:

- **`channel: "whatsapp"`** — запросить код на номер, у которого WhatsApp есть;
- **`channel: "sms"`** — на проде сейчас **не воспроизводится**: у номера без
  WhatsApp шлюз ответит ошибкой, а SMS не уйдёт из-за тестового аккаунта, и
  придёт пустой `channel`. Ветку `"sms"` проверяйте на стенде или подменой
  ответа — глазами на проде её увидеть не получится.

Проверьте оба варианта: экран не должен обещать WhatsApp, когда пришла SMS.

---

## 7. Чего делать НЕ надо

- Не подключать в приложение никакие SDK WhatsApp — доставка целиком на
  бэкенде, приложение только читает `channel`.
- Не выбирать канал со стороны клиента: параметра для этого нет, порядок
  каналов задаётся на сервере.
- Не завязываться на строку `detail` — она осталась прежней ради старых
  сборок и в будущем может измениться.
- Не убирать SMS-автозаполнение — для `channel: "sms"` оно работает.

---

## 8. Приёмка

- [ ] `channel: "whatsapp"` → экран говорит про WhatsApp
- [ ] `channel: "sms"` → экран говорит про SMS, автозаполнение работает
      (проверяется на стенде: на проде SMS сейчас не уходит)
- [ ] Экран «не приходит код» говорит про WhatsApp, а не про SMS
- [ ] `channel: ""` → нейтральный текст, без обещания канала
- [ ] Повторная отправка со сменой канала — текст на экране обновился
- [ ] Кнопка «Отправить повторно» заблокирована 60 с, отсчёт переживает сворачивание
- [ ] Слово «SMS» не осталось в текстах, которые показываются при доставке в WhatsApp
- [ ] Код из WhatsApp вставляется в поле через буфер обмена

---

## 9. Заметка на будущее

Сейчас WhatsApp работает через self-hosted шлюз на обычном аккаунте — решение
временное, до подключения Meta Cloud API. Для приложения переход будет
незаметен: контракт и значения `channel` не изменятся.

# Проверка кода отдельным шагом — `check-code`

Задача приложению: показывать ошибку неверного кода **на экране ввода кода**,
а не после того, как человек заполнит анкету.

Новый эндпоинт уже работает на проде. `verify-code` не менялся — выпущенные
сборки продолжают работать.

---

## 1. Что было сломано

Регистрация идёт в два экрана: сначала код, потом ФИО и ПВЗ. Проверить код на
первом экране было нечем — единственный подходящий запрос `verify-code` у
нового клиента требует ещё и анкету:

```python
verify_sms_code(...)                    # ← код уже погашен здесь
if is_new_user and (not pickup_point or not full_name):
    raise ValidationError(...)          # ← а ошибка только здесь
```

Порядок был такой, что код помечался использованным **раньше**, чем
проверялись обязательные поля. Итог: клиент вводил правильный код, получал
ошибку, а код уже сгорел — и новый приходил только через минуту из-за
троттлинга.

Отсюда же типичная жалоба «ввожу код, пишет ошибка, потом вообще не приходит».

---

## 2. Эндпоинт

```http
POST /api/auth/check-code/
Content-Type: application/json

{ "phone": "+996700000000", "code": "1234", "cargo_id": 4 }
```

**Успех — `200`:**

```json
{ "valid": true, "is_new_user": true }
```

| Поле | Смысл |
|---|---|
| `valid` | код верный; всегда `true` при `200` |
| `is_new_user` | `true` — клиента нет, нужна анкета; `false` — есть, анкету пропустить |

**Ошибка — `400`:**

```json
["Invalid or expired SMS code"]
```

Один и тот же ответ на неверный, истёкший и чужой код — намеренно: по тексту
ошибки нельзя определить, существует ли код и для какого он карго.

Отдельно `400` с текстом `Too many attempts. Request a new code.` — попытки
исчерпаны, нужен новый код.

**Ключевое: код не гасится.** После `check-code` тот же код уходит в
`verify-code`. Проверять можно сколько угодно раз — верный код остаётся верным.

---

## 3. Попытки и троттлинг

- **5 неверных попыток** на код — потом он сжигается, нужен новый.
  Попытки считаются и в `check-code`, и в `verify-code`: иначе проверка без
  сжигания превратилась бы в бесплатный перебор четырёх цифр.
- **60 секунд** между запросами кода на пару номер + карго (`send-code` → `429`).
  На `check-code` это ограничение не действует — проверять можно сразу.

Практический вывод для интерфейса: после `400` **не запрашивай новый код
автоматически**. У человека ещё есть попытки, а автозапрос упрётся в
троттлинг. Дай ввести заново.

---

## 4. Порядок работы

```
экран телефона
  └─ POST send-code            → { channel }
экран кода
  └─ POST check-code           → 400  → «Неверный код», остаёмся здесь
                               → 200  → смотрим is_new_user
                                          ├─ true  → экран анкеты (ФИО, ПВЗ)
                                          └─ false → сразу шаг ниже
завершение
  └─ POST verify-code          → access / refresh / user
     (тот же код, что проверяли)
```

Для существующего клиента `check-code` можно не звать — `verify-code`
отработает сразу. Но проще звать всегда: один путь на оба случая, и ошибка
показывается там, где человек её допустил.

---

## 5. Завершение: `verify-code`

Не изменился, гасит код и выдаёт токены:

```http
POST /api/auth/verify-code/

{ "phone": "+996700000000", "code": "1234", "cargo_id": 4,
  "pickup_point_id": 2, "full_name": "Иван Иванов" }
```

`pickup_point_id` и `full_name` обязательны только при регистрации
(`is_new_user: true`). ПВЗ обязан принадлежать тому же карго, иначе `400`.

Ответ: `access`, `refresh`, `user`, `is_new_user`.

---

## 6. Частные случаи

**Мастер-код.** Резервный код поддержки проходит `check-code` так же, как
`verify-code`, и возвращает `200`. Приложению ничего специально делать не надо.

**Тестовый номер для ревью в сторах.** Фиксированный код, не истекает и не
гасится. `check-code` на нём возвращает `200` сколько угодно раз.

**Код от другого карго.** Коды привязаны к карго: выданный для карго A не
подойдёт под карго B — `400`. Следи, чтобы `cargo_id` в `send-code`,
`check-code` и `verify-code` был один и тот же.

**Смена номера на экране кода.** Если человек вернулся и поменял телефон,
старый код недействителен — запрашивай новый через `send-code`.

---

## 7. Что поменять в приложении

1. На экране кода вызывать `check-code` вместо перехода дальше вслепую.
2. `400` — показывать ошибку под полем и **оставаться на экране**, не
   переходить к анкете и не запрашивать новый код автоматически.
3. По `is_new_user` решать, показывать ли анкету, — а не ловить это из ошибки
   `verify-code`.
4. Сохранить введённый код до конца сценария: в `verify-code` уходит он же.

---

## 8. Приёмка

- [ ] Неверный код → ошибка на экране кода, анкета не открывается
- [ ] Верный код → переход дальше; при `is_new_user: false` анкета пропущена
- [ ] После `check-code` тот же код успешно проходит `verify-code`
- [ ] Повторный `check-code` с верным кодом снова даёт `200` (код не сгорел)
- [ ] 5 неверных попыток → сообщение о том, что нужен новый код
- [ ] После неверного кода приложение **не** дёргает `send-code` само
- [ ] `cargo_id` одинаков во всех трёх запросах
